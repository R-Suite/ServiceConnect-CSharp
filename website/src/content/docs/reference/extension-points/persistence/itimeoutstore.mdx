## Overview

`ITimeoutStore` persists scheduled timeout messages and delivers them in batches when they become due. The timeout manager polls `GetTimeoutsBatchAsync` on a schedule driven by the recommended poll time returned in each batch, inserts new timeouts via `InsertTimeoutAsync`, and commits or rolls back each dispatch with `RemoveDispatchedTimeoutAsync` or `ReleaseDispatchedTimeoutAsync`.

`ITimeoutStore` is the base interface suitable for single-instance deployments. Multi-instance deployments should use [`ILeaseAwareTimeoutStore`](/ServiceConnect-CSharp/reference/extension-points/persistence/ileaseawaretimeoutstore/) instead.

See [Process Manager](/ServiceConnect-CSharp/learn/messaging-patterns/process-manager/) for the saga and timeout conceptual model.

## Reference

```csharp
public interface ITimeoutStore
{
    Task InsertTimeoutAsync(TimeoutData timeoutData, CancellationToken cancellationToken = default);
    Task<TimeoutsBatch> GetTimeoutsBatchAsync(CancellationToken cancellationToken = default);
    Task RemoveDispatchedTimeoutAsync(Guid id, CancellationToken cancellationToken = default);
    Task ReleaseDispatchedTimeoutAsync(Guid id, CancellationToken cancellationToken = default);
}
```

`TimeoutData` carries the timeout identifier, target destination, scheduled fire time, and an `IReadOnlyDictionary<string, object>` headers bag. Implementations that construct `TimeoutData` pass any headers via the init accessor; post-construction mutation is not supported. `TimeoutsBatch` wraps a list of due `TimeoutData` records together with a `NextQueryTime` that tells the manager when to poll again.

### `InsertTimeoutAsync`

```csharp
Task InsertTimeoutAsync(TimeoutData timeoutData, CancellationToken cancellationToken = default);
```

Inserts a timeout into the store.

**Parameters**
- `timeoutData` — the timeout to persist.
- `cancellationToken` — a token that cancels the operation.

---

### `GetTimeoutsBatchAsync`

```csharp
Task<TimeoutsBatch> GetTimeoutsBatchAsync(CancellationToken cancellationToken = default);
```

Loads the next batch of due timeouts.

**Parameters**
- `cancellationToken` — a token that cancels the operation.

**Returns** the due timeouts and the next recommended poll time. The caller uses the recommended poll time to back off until the next batch may be ready, avoiding tight polling loops when no timeouts are due.

---

### `RemoveDispatchedTimeoutAsync`

```csharp
Task RemoveDispatchedTimeoutAsync(Guid id, CancellationToken cancellationToken = default);
```

Removes a timeout after it has been dispatched successfully.

**Parameters**
- `id` — the timeout identifier.
- `cancellationToken` — a token that cancels the operation.

**Remarks.** Call this after the timeout message has been delivered to the downstream consumer and acknowledged. The operation must be idempotent — the manager may retry on transient storage failures, so a second call for the same `id` should succeed silently (no-op).

---

### `ReleaseDispatchedTimeoutAsync`

```csharp
Task ReleaseDispatchedTimeoutAsync(Guid id, CancellationToken cancellationToken = default);
```

Releases a dispatched timeout so it may be retried later.

**Parameters**
- `id` — the timeout identifier.
- `cancellationToken` — a token that cancels the operation.

**Remarks.** Call this when dispatch fails — the consumer rejected the message, transport delivery failed, or the timeout is being requeued for retry. After a successful release the timeout is visible on the next `GetTimeoutsBatchAsync` call. Like `RemoveDispatchedTimeoutAsync`, this operation must be idempotent.

## Implementing

### Invariants

1. **Concurrent callers.** `GetTimeoutsBatchAsync` must not return the same timeout to two concurrent callers without locking. The built-in `InMemoryTimeoutStore` uses a `ReaderWriterLockSlim` and a per-record lease; a SQL implementation should use `FOR UPDATE SKIP LOCKED` (Postgres) or an equivalent. In clustered setups where multiple bus instances share the same persistent store, implement [`ILeaseAwareTimeoutStore`](/ServiceConnect-CSharp/reference/extension-points/persistence/ileaseawaretimeoutstore/) instead so that lease ownership is verified on removal and release.

2. **Idempotency.** `RemoveDispatchedTimeoutAsync` and `ReleaseDispatchedTimeoutAsync` must be idempotent. The manager may retry either call on transient storage failures. A second call for an already-removed or already-released record should be a silent no-op.

### Timeout lease semantics

`RemoveDispatchedTimeoutAsync` and `ReleaseDispatchedTimeoutAsync` accept an optional lock owner when called on an [`ILeaseAwareTimeoutStore`](./ileaseawaretimeoutstore/). When supplied, the operation is lease-checked: a worker that no longer holds a valid lease observes `ConcurrencyException` so the row is not double-dispatched by a second worker that reclaimed it.

Both the Mongo and InMemory persistors honour identical semantics. The `LockLeaseDuration` setting — `MongoDbPersistenceOptions.TimeoutLockLeaseDuration` or `InMemoryPersistenceOptions.LockLeaseDuration` — governs how long a worker may hold a row before the reaper reclaims it. Both default to five minutes.

Operators running the Mongo persistor should call `ReapStaleLeasesAsync` on a timer at roughly `LockLeaseDuration / 4` cadence to reclaim rows held by crashed handlers promptly.

### Skeletal in-memory implementation

The `InMemoryTimeoutStore` shipped with the library (in `ServiceConnect.Persistence.InMemory`) is the reference single-instance implementation. It stores timeouts in a sorted set, uses a write lock for all mutations, and reads its lease duration from `InMemoryPersistenceOptions` so that a crashed dispatcher does not hold records indefinitely. The constructor accepts an options instance:

```csharp
public sealed class InMemoryTimeoutStore : ITimeoutStore
{
    private readonly ReaderWriterLockSlim _lock = new();
    private readonly SortedSet<TimeoutEntry> _index = new(TimeoutEntryComparer.Instance);
    private readonly Dictionary<Guid, TimeoutEntry> _byId = new();
    private readonly TimeSpan _lockLeaseDuration;

    public InMemoryTimeoutStore(InMemoryPersistenceOptions options)
    {
        ArgumentNullException.ThrowIfNull(options);
        if (options.LockLeaseDuration <= TimeSpan.Zero)
            throw new ArgumentOutOfRangeException(nameof(options), "LockLeaseDuration must be positive.");
        _lockLeaseDuration = options.LockLeaseDuration;
    }

    public Task InsertTimeoutAsync(TimeoutData timeoutData, CancellationToken cancellationToken = default)
    {
        _lock.EnterWriteLock();
        try
        {
            var entry = new TimeoutEntry(timeoutData.Time, timeoutData.Id, timeoutData);
            _byId[timeoutData.Id] = entry;
            _index.Add(entry);
        }
        finally { _lock.ExitWriteLock(); }
        return Task.CompletedTask;
    }

    public Task<TimeoutsBatch> GetTimeoutsBatchAsync(CancellationToken cancellationToken = default)
    {
        var batch = new TimeoutsBatch { DueTimeouts = [] };
        var utcNow = DateTimeOffset.UtcNow;

        _lock.EnterWriteLock();
        try
        {
            foreach (var entry in _index)
            {
                if (entry.Time <= utcNow && (!entry.Data.Locked || entry.Data.LockExpiresAt <= utcNow))
                {
                    entry.Data.Locked = true;
                    entry.Data.LockExpiresAt = utcNow + _lockLeaseDuration;
                    batch.DueTimeouts.Add(entry.Data);
                }
                else if (entry.Time > utcNow)
                {
                    break;
                }
            }
        }
        finally { _lock.ExitWriteLock(); }

        return Task.FromResult(batch);
    }

    public Task RemoveDispatchedTimeoutAsync(Guid id, CancellationToken cancellationToken = default)
    {
        _lock.EnterWriteLock();
        try
        {
            if (_byId.TryGetValue(id, out var entry))
            {
                _byId.Remove(id);
                _index.Remove(entry);
            }
        }
        finally { _lock.ExitWriteLock(); }
        return Task.CompletedTask;
    }

    public Task ReleaseDispatchedTimeoutAsync(Guid id, CancellationToken cancellationToken = default)
    {
        _lock.EnterWriteLock();
        try
        {
            if (_byId.TryGetValue(id, out var entry))
            {
                entry.Data.Locked = false;
                entry.Data.LockExpiresAt = null;
            }
        }
        finally { _lock.ExitWriteLock(); }
        return Task.CompletedTask;
    }
}
```

## Relationship to ILeaseAwareTimeoutStore

`ITimeoutStore` is the right choice for single-instance deployments: only one timeout manager polls the store at a time, so there is no risk of two callers claiming and dispatching the same timeout record simultaneously.

In multi-instance (active-active) deployments where several bus instances share the same persistent store, use [`ILeaseAwareTimeoutStore`](./ileaseawaretimeoutstore/) instead. The lease-aware variant requires callers to prove they still hold the lock on a record before the store will remove or release it. This prevents duplicate dispatch when the instance that originally claimed a timeout crashes before calling `RemoveDispatchedTimeoutAsync` and another instance subsequently claims the same record.

Implementations typically satisfy both interfaces on one class and are registered twice in the DI container — once for each interface — so the dispatcher can use whichever overloads are appropriate.

## Usage

Register a custom `ITimeoutStore` implementation during bus startup:

```csharp
services.AddServiceConnect(builder =>
{
    builder.UseRabbitMQ(transport => transport.Host = "rabbit.internal.example");
    builder.AddRegistration(services =>
    {
        services.AddSingleton<ITimeoutStore, YourTimeoutStore>();
    });
});
```

For multi-instance deployments, register a type that implements both interfaces and alias it to each:

```csharp
builder.AddRegistration(services =>
{
    services.AddSingleton<YourLeaseAwareStore>();
    services.AddSingleton<ITimeoutStore>(sp => sp.GetRequiredService<YourLeaseAwareStore>());
    services.AddSingleton<ILeaseAwareTimeoutStore>(sp => sp.GetRequiredService<YourLeaseAwareStore>());
});
```

## MongoDB timeout-store contract

### WriteConcern.Unacknowledged rejected

`MongoDbTimeoutStore` requires the `IMongoClient` to be configured with an acknowledged write concern (`w:1` or higher). Construction throws `InvalidOperationException` for `WriteConcern.Unacknowledged`. Under `w:0`, lock-aware delete and release operations silently no-op-succeed — converting a stale-lease no-op into an apparent successful delete and admitting duplicate timeout dispatch.

See [Persistence Configuration → MongoDB provider contract](/ServiceConnect-CSharp/reference/configuration/ipersistenceconfiguration/#writeconcern-requirement) for the full guard set across all three Mongo stores.
